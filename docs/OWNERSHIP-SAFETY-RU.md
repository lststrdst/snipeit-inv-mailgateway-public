# Защита от случайной смены пользователя

Я перенёс окончательное решение о владельце компьютера на Gateway. Агент только
сообщает, какую интерактивную учётную запись увидел Windows; одного такого
наблюдения недостаточно для изменения актива в Snipe-IT.

## Какие учётные записи принимаются

По умолчанию принимается только строгий формат
`инициал.фамилия`: регулярное выражение
`^[a-z]\.[a-z]+(?:-[a-z]+)?$`. Поэтому административные варианты с
дополнительным суффиксом, машинные, системные и технические учётные записи не
проходят проверку. Дополнительно отбрасываются известные Windows/service
имена и префиксы `ad_`, `svc_`, `service_`, `dwm-`, `umfd-`.

Для реальных пользователей с нестандартным историческим именем я предусмотрел
явный allow-list `ownership.non_standard_accounts` на Gateway. В него попадают
только заранее согласованные точные логины; остальные имена вне формата
`инициал.фамилия` автоматически отклоняются. Агент использует такой же список
`NonStandardAccounts` и передаёт имя как есть.

## Как подтверждается новый владелец

Я использую следующий автомат состояний:

```text
новое имя → кандидат (1 наблюдение)
то же имя → 2 наблюдения
то же имя, не менее 3 событий и 24 часов → подтверждённый владелец
другое имя до подтверждения → предыдущий кандидат сброшен
пустое/запрещённое имя → текущий владелец сохранён без изменений
```

По умолчанию нужны три разных `event_id`, распределённых минимум на 24 часа.
Кандидат протухает через 7 дней. Повторная доставка одного события не
увеличивает счётчик. Если компьютер каждый день показывает разных
пользователей, ни один из них не наберёт стабильность и актив не будет
перепривязан.

После подтверждения Gateway ищет ровно одно полное совпадение `username` в
Snipe-IT. Ноль или несколько совпадений означают `preserve`: инвентаризация
обновляется, назначение не меняется. Пустой username никогда не выполняет
check-in и не переводит актив «на никого».

Письмо «Смена пользователя» создаётся только после фактической пары
check-in/checkout в Snipe-IT, а не после каждого сообщения агента.

## Где хранится состояние

Кандидаты, число подтверждений, первая/последняя дата и последний `event_id`
хранятся в таблице `owner_candidates` той же durable SQLite БД. Состояние
переживает перезапуск worker и не зависит от конкретного транспорта: HTTPS и
SMTP fallback дают одинаковый результат.

Параметры можно менять только в закрытом server config:

```json
{
  "ownership": {
    "username_pattern": "^[a-z]\\.[a-z]+(?:-[a-z]+)?$",
    "non_standard_accounts": ["LegacyUserA", "LegacyUserB"],
    "confirmation_events": 3,
    "confirmation_hours": 24,
    "candidate_window_days": 7
  }
}
```
